Analysis

1 · T1–T4 and a single evaluation are linear

Between 1,000 and 1,000,000 random-formula nodes (a factor of 1000) the log-log slope of every iterative function lies between 0.96 and 1.10: tokenize 1.01, infixToPrefix 0.98, prefixToTree 0.96, inorderIter 0.96, preorderIter 0.97, postorderIter 0.96, heightIter 1.10, evaluateIter 1.00, freeTree 0.96. A slope of 1 is linear; the plot on the Results page shows all curves parallel to the O(n) reference. This matches the analysis: every token or node is pushed and popped a constant number of times. Slopes slightly above 1 at the top end are probably the working set outgrowing the CPU caches (a 1M-node tree is ≈ 64 MB); we did not test this.

One exception worth knowing: collectAtoms is O(n + k log k). On a chain of 1,000,000 nodes there are k ≈ 500,000 distinct atoms, and sorting them with the allocation-heavy natural-order comparator takes 1,009 ms against 37.2 ms at 100,000 nodes: a factor of 27 for 10× the nodes. Everything else stays linear.

2 · Recursive vs. iterative: same Big-O, different stack

On trees that do not overflow, the two versions cost about the same: for example inorderRec 9.52 ms vs. inorderIter 11.5 ms on 1,000,000 random nodes. The difference is where the O(h) bookkeeping lives. The recursive code uses the thread's call stack, limited to 8 MB here; the iterative code uses a std::vector on the heap, limited only by memory.

The crash experiment shows the consequence. On a left-deep chain the recursion depth equals the height, and the recursive in-order, pre-order, post-order and evaluation functions died between 174,500 and 175,000 levels (≈ 48 bytes per call), and heightRec between 523,500 and 524,000 (≈ 16 bytes per call: a smaller frame). The iterative versions processed trees of height 879,756 (the largest SAT file) without trouble, and so did the iterative freeTree. The SAT files fifo8_200 (height 353,514) and cache_10 (879,756) crash every recursive function in the left-deep shape. This is why the CLI refuses to run recursive variants above height 10,000.

3 · Effect of tree shape

For the same formula the two CNF shapes give the same node count but very different heights, and the auxiliary structures move in opposite directions. On cache_10 (5,479,586 nodes):

A DFS stack (traversals, evaluation, prefixToTree) is as deep as the tree is tall: 879,757 entries for the left-deep tree against 54 for the balanced one. A BFS queue is as large as the widest level: 20 for the left-deep tree against 1,622,213 entries for the balanced one. So the iterative height trades call-stack depth for queue width, and which one is cheaper depends on the shape. Balancing reduces the height from 879,756 to 53, which turns the recursive code from "crashes" to "safe", but a balanced tree is not free: its BFS queue holds about a third of all nodes.

4 · Why the truth table is infeasible for SAT instances

A truth table has 2k rows and each row costs one O(n) evaluation, so O(2k·n) in total. Measured on 100-node formulas: k = 4 → 31 µs, k = 12 → 6.87 ms, k = 17 → 218 ms, i.e. a roughly constant ≈ 1.7 µs per row, so the time doubles with every extra atom (the generator did not always use all requested atoms; the table lists the real counts). Extrapolating that rate to k = 50 (a small SAT instance) gives 250 ≈ 1.1·1015 rows ≈ 59 years for a 100-node formula, and far more for real formulas; the benchmark files have between 26 and 227,210 variables. That is why printTruthTable refuses above 20 atoms. The brute-force table is exactly the exponential procedure that SAT solvers are designed to avoid: deciding satisfiability is NP-complete (Cook–Levin), so no known algorithm for the general problem avoids exponential worst-case time, although evaluating one assignment — checking a certificate — is the linear-time operation measured in section 1.

5 · Memory

sizeof(Node) is 56 bytes on this 64-bit build: 4 (type) + 4 (padding) + 32 (std::string) + 8 + 8 (two pointers). malloc rounds each allocation to a 64-byte chunk, so a tree costs ≈ 64 bytes per node; 5,479,586 nodes (cache_10) ≈ 351 MB for the tree alone. Atom names such as x227210 are 7 characters, below libstdc++'s 15-character small-string limit, so they live inside the node and add no heap allocation (SSO). The whole pipeline is larger than the tree: the token vector, the prefix vector and the tree all exist at once, which is why the CLI peaked at 1,027 MB on this file (≈ 187 bytes per node overall, measured with RUSAGE_CHILDREN-style peak RSS).

An index-based node pool would store each node as a type byte, two 32-bit child indices and a 32-bit symbol id (atoms interned once): about 13 bytes instead of 64, roughly a 5× reduction, better cache behaviour, and one free instead of millions. We did not implement this (the assignment makes it optional); the figure is an estimate, not a measurement.

Limitations

  • One machine, one compiler, one run of each benchmark; medians of 5 repetitions. Differences below ~10% should not be read as real.
  • rss_kb for in-process rows is the process peak so far and only grows; for forked rows it is the child's own peak. It is therefore a rough memory indicator, not a per-function cost.
  • The benchmark binary is built with -DBENCH_INSTRUMENT (stack/queue counters). We did not measure the counters' own overhead separately; the crash depths come from a separate binary without them.
  • The instrumented recursive functions' stack frames differ slightly from the production ones, so a recursive row can crash at a different height in bench than in the crash-depth search.
